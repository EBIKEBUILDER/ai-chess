Architectural Specification and System Blueprint: Next.js 3D WebGL Chess Platform with Stateful Multi-Provider AI Orchestration

Executive System Architecture and Paradigm Shift

Modern browser-based simulation software requires a fundamental decoupling between high-frequency visual rendering and asynchronous, stateful artificial intelligence computation1. When constructing a lightweight 3D chess application in Next.js, the primary engineering challenge lies in synchronizing a 60-frames-per-second (FPS) WebGL scene graph with multi-second Large Language Model (LLM) deliberation cycles without introducing main-thread blocking, state desynchronization, or network payload bloat1. Traditional web chess architectures either rely on heavy binary 3D asset downloads (.glb or .gltf files) that degrade initial page load performance or utilize stateless LLM completion endpoints that resend the entire Portable Game Notation (PGN) history, chat transcript, and thought history on every ply1. In a standard 60-move (120-ply) chess match, stateless context re-transmission creates quadratic token growth (), inflating API latency and exhausting token budgets while stripping the model of its encrypted internal thought continuity across turns1.

This specification establishes a unified, production-grade blueprint designed for direct ingestion by automated software engineering agents. The architecture resolves rendering bloat through procedural 3D geometry synthesis inside @react-three/fiber and @react-three/drei, achieving an initial JavaScript footprint near 79 KB, a Time-to-Live (TTL) under 100 milliseconds, and a Lighthouse performance score of 1002. Simultaneously, it eliminates quadratic token overhead by adopting Google's Generally Available Interactions API (@google/genai SDK v2.3.0+) alongside OpenAI's Responses API, leveraging server-side state chaining (previous_interaction_id and previous_response_id) to maintain continuous multi-turn memory on provider infrastructure1.

The architectural separation enforces a strict single-source-of-truth paradigm9. Every action within the platform—whether initiated by a human dragging or clicking a 3D mesh across the board, typing a Standard Algebraic Notation (SAN) string into the command bar, receiving a move from an autonomous AI opponent, or applying a demonstration line from the AI Chess Teacher—is encapsulated as an immutable Command object4. This Command object must pass through the chess.js validation gate before mutating the central state store or triggering 3D coordinate interpolation3.

Furthermore, coupling the deterministic chess.js engine with server-side stateful LLM sessions transforms how language models participate in board games1. When an LLM is invoked via client.interactions.create with a previous_interaction_id, Google's backend automatically reconstructs the preceding conversation steps—including the encrypted signature fields attached to prior thought steps1. Consequently, a model such as gemini-4-argon or gemini-3.8-flash does not merely evaluate an isolated board snapshot; it retains the strategic plan it formulated on earlier turns, verifies whether its opponent refuted that plan, and outputs both its internal thought summary and a schema-validated JSON move payload6.

Critical Nuances of Server-Side State (previous_interaction_id)

The Interactions API stores completed interactions on the server by default (store: true)1. To continue a multi-turn chess match or coaching dialogue without re-transmitting the history array, the backend passes the id of the prior turn's response into the previous_interaction_id field of the subsequent client.interactions.create call1. Server-side chaining yields two major engineering advantages: first, encrypted thought signatures are managed automatically on Google's servers without manual client-side step reconstruction; second, implicit prompt caching hit rates increase substantially, lowering turn latency and token cost across long games1.

Examination of the Interactions API specification reveals three critical operational constraints that coding agents must enforce to prevent silent runtime failures1. First, configuration parameters are strictly interaction-scoped: while previous_interaction_id preserves the conversation history of inputs, thoughts, and outputs, parameters such as system_instruction, response_format, and generation_config (thinking_level, thinking_summaries, max_output_tokens) do not persist across chained turns and must be re-specified on every call to client.interactions.create1. Second, legacy sampling parameters must be omitted: in the Gemini 4 and Gemini 3.6+ model families, custom values for temperature, top_p, and top_k are ignored by the inference engine, so the backend adapter must omit them from generation_config and rely on thinking_level and seed for behavioral control14. Third, structured outputs use a top-level response_format schema configuration (response_format: { type: "text", mime_type: "application/json", schema: jsonSchemaObject }) rather than the nested config.responseSchema structure of the legacy generateContent endpoint11. The resulting JSON string is retrieved via the interaction.output_text convenience property and parsed at runtime using Zod (z.fromJSONSchema(jsonSchemaObject).parse(JSON.parse(interaction.output_text)))11.

Lightweight 3D WebGL Rendering Architecture in Next.js

Procedural Lathe and Extrude Geometry Synthesis

To satisfy the requirement for a fast-loading, lightweight 3D browser experience that still achieves high visual polish, the rendering layer eliminates external 3D asset files (.glb and .gltf) in favor of procedural geometry generation2. External 3D models require asynchronous network fetching, Draco decompression workers, and GPU texture uploads that delay First Contentful Paint5. By contrast, classical Staunton chess pieces possess axial symmetry, meaning Pawns, Rooks, Bishops, Queens, and Kings can be mathematically defined as 2D vector profiles (THREE.Vector2 arrays) revolved  around the vertical Y-axis using THREE.LatheGeometry7. The Knight, which is asymmetric along the X/Z plane, is generated via a 2D horse-head contour (THREE.Shape) extruded with beveled edges using THREE.ExtrudeGeometry mounted atop a lathed cylindrical base7.

Memoizing these geometries inside React (useMemo) ensures that the GPU compiles only six unique vertex buffers at startup, totaling less than 4 KB of TypeScript code and zero network asset requests2. Visual fidelity is achieved through physically based materials (meshPhysicalMaterial with clearcoat, subtle roughness variation, and environment reflections via @react-three/drei's <ContactShadows>) rather than high-polygon external meshes25.

Persistent Piece Identity and Frame-Rate Decoupling

A common defect in React Three Fiber chess implementations occurs when the 3D scene renders pieces by iterating directly over the 8x8 2D array returned by chess.board()3. Because chess.board() only reports the piece type and color currently occupying each square ({ square: 'e4', type: 'p', color: 'w' }), moving a pawn from e2 to e4 causes React to unmount the mesh at e2 and mount a brand-new mesh at e4, destroying any possibility of smooth 3D movement animation3.

To achieve fluid 60 FPS piece gliding and knight-jump arcs, the application state store maintains a persistent TrackedPiece registry mapped to chess.js moves3. At game initialization, all 32 pieces receive immutable unique identifiers (w-p-a2, b-n-g8, etc.)3. Whenever a move command ({ from: 'e2', to: 'e4' }) is executed, the store updates the square property of the existing TrackedPiece object (w-p-e2 updates its target coordinates from e2 to e4), marks any captured piece at to (or the en passant capture square) as captured: true, and updates rook coordinates during castling (flags containing 'k' or 'q')3. Inside the <ProceduralPieceMesh> component, a useFrame hook interpolates (THREE.MathUtils.lerp) the mesh's live 3D position toward its target board coordinates with a vertical transit arc during active movement3.

Autonomous AI-vs-AI Match Loop and Self-Correction Protocol

When the user configures White as gemini-4-argon (for instance, with thinking_level: "high") and Black as gemini-3.8-flash (thinking_level: "low") or OpenAI gpt-5.5, the match orchestrator enters an autonomous execution loop6. Rather than invoking while (!chess.isGameOver()) in a synchronous blocking loop—which would freeze the browser's main rendering thread—the orchestrator utilizes a reactive turn watcher keyed to the current FEN, match status ("playing" | "paused" | "idle" | "gameover"), and an incrementing sessionId cancellation token9.

When an AI seat is scheduled to move, the orchestrator first executes a terminal condition guard via chess.isGameOver(), since querying chess.moves() on a checkmated, stalemated, or drawn board returns an empty array9. Next, to prevent the language model from hallucinating illegal moves, the server route extracts the exact array of legal moves via chess.moves() and enriches the turn prompt with the current FEN, the opponent's last SAN move, the ASCII board representation (chess.ascii()), and the complete list of legal SAN strings4. The server then invokes client.interactions.create with previous_interaction_id (or client.responses.create with previous_response_id) so the model retains its full strategic memory from prior turns1. Once the model responds with structured JSON, the backend validates the proposed move against a scratch new Chess(currentFen) instance4. If the model proposes a move outside the legal list, the server immediately chains a self-correction interaction using the newly returned interaction.id as previous_interaction_id, informing the model why the move was rejected and instructing it to select strictly from the legal SAN array1. Once validated, the client Command Bus executes the move, appends the model's thought summary and conversational table-talk message to the live log, updates the persisted interactionId for that seat, waits for a user-configurable pacing delay (100ms to 2500ms) so the 3D piece glide completes visibly, and triggers the opposing AI's turn6.

Pedagogical Architecture: The Interactive AI Chess Teacher

Language models frequently struggle when asked to teach chess from a raw FEN string alone because tokenizing slash-separated FEN notation (r1bqkbnr/pppp1ppp/2n5/4p3/4P3/5N2/PPPP1PPP/RNBQKB1R w KQkq - 2 3) requires complex spatial reconstruction of diagonals, files, and knight-hop vectors4. The AI Chess Teacher Mode overcomes this limitation by combining chess.js programmatic board inspection with gemini-4-argon or gemini-3.8-flash stateful coaching1.

Before sending a coaching request or student question to the Gemini Interactions API, the backend executes a deterministic Tactical Pre-Processor using chess.js methods26. It first evaluates chess.inCheck(), chess.isCheckmate(), chess.isStalemate(), and chess.isDraw() to establish terminal or check states29. It then iterates across all occupied squares from chess.board() and queries chess.attackers(square, 'w') and chess.attackers(square, 'b')26. Because chess.attackers() returns every square whose piece attacks the target square regardless of whether a piece is pinned, the pre-processor constructs an exact, hallucination-free tactical telemetry map showing which pieces are undefended (hanging), under-defended, or contested26. Finally, it enumerates verbose legal moves (chess.moves({ verbose: true })) to identify available captures, checks, and promotions4.

This pre-computed tactical digest is injected into the input of client.interactions.create alongside the student's move or question, chained via previous_interaction_id so the AI Chess Teacher remembers concepts already taught earlier in the session1. Constrained by a strict JSON Schema (response_format), the AI Teacher returns a pedagogical classification of the student's last move ("brilliant", "good", "inaccuracy", "mistake", or "blunder"), a clear coaching explanation, up to three recommended candidate moves with strategic justifications, and 3D board annotations (visual_highlights and visual_arrows) that the React Three Fiber canvas renders directly over the 3D chessboard as glowing square overlays and elevated 3D vector arrows11.

3. Google Gemini Interactions API Adapter (src/lib/ai/gemini-interactions.ts)

This module implements the exact @google/genai v2.3.0+ Interactions API syntax, enforcing the exclusive model list (gemini-4-argon and gemini-3.8-flash), thinking_level ("low", "medium", "high"), thinking_summaries: "auto", server-side state management via previous_interaction_id, interaction-scoped parameter re-injection, and Zod schema parsing via z.fromJSONSchema1.

// src/lib/ai/gemini-interactions.ts
import { GoogleGenAI } from "@google/genai";
import * as z from "zod";
import type { GeminiModelId, ThinkingLevel } from "@/types/chess";

const ALLOWED_GEMINI_MODELS: ReadonlySet<string> = new Set([
 "gemini-4-argon",
 "gemini-3.8-flash",
]);

const ALLOWED_THINKING_LEVELS: ReadonlySet<string> = new Set([
 "low",
 "medium",
 "high",
]);

const aiClient = new GoogleGenAI({
 apiKey: process.env.GEMINI_API_KEY,
});

export interface GeminiStructuredInteractionParams {
 model: GeminiModelId;
 thinkingLevel: ThinkingLevel;
 systemInstruction: string;
 inputPrompt: string;
 jsonSchema: Record<string, unknown>;
 previousInteractionId?: string | null;
}

export interface GeminiInteractionResult<T> {
 parsedOutput: T;
 interactionId: string;
 thoughtSummaryText: string | null;
 totalThoughtTokens: number | null;
 latencyMs: number;
}

/**
* Executes a stateful turn using the Google Gemini Interactions API (GA June 2026).
* Preserves conversation memory server-side via previous_interaction_id while re-specifying
* interaction-scoped parameters (system_instruction, generation_config, response_format).
*/
export async function executeGeminiStructuredInteraction<T>(
 params: GeminiStructuredInteractionParams
): Promise<GeminiInteractionResult<T>> {
 if (!ALLOWED_GEMINI_MODELS.has(params.model)) {
   throw new Error(
     `Invalid Gemini model "${params.model}". Only "gemini-4-argon" and "gemini-3.8-flash" are permitted.`
   );
 }

 if (!ALLOWED_THINKING_LEVELS.has(params.thinkingLevel)) {
   throw new Error(
     `Invalid thinking_level "${params.thinkingLevel}". Permitted values: "low", "medium", "high".`
   );
 }

 const startTime = performance.now();

 // Build the Interactions API payload.
 // Note: temperature, top_p, and top_k are intentionally omitted as Gemini 4 and 3.8 ignore them.
 const requestPayload: Record<string, unknown> = {
   model: params.model,
   input: params.inputPrompt,
   system_instruction: params.systemInstruction,
   store: true,
   generation_config: {
     thinking_level: params.thinkingLevel,
     thinking_summaries: "auto",
     max_output_tokens: 2048,
   },
   response_format: {
     type: "text",
     mime_type: "application/json",
     schema: params.jsonSchema,
   },
 };

 if (params.previousInteractionId) {
   requestPayload.previous_interaction_id = params.previousInteractionId;
 }

 // Call the Interactions API endpoint
 const interaction: any = await (aiClient as any).interactions.create(requestPayload);

 const latencyMs = Math.round(performance.now() - startTime);

 // Extract chronological thought summaries from interaction.steps
 const thoughtSegments: string[] = [];
 if (Array.isArray(interaction.steps)) {
   for (const step of interaction.steps) {
     if (step.type === "thought" && Array.isArray(step.summary)) {
       for (const contentBlock of step.summary) {
         if (contentBlock.type === "text" && typeof contentBlock.text === "string") {
           thoughtSegments.push(contentBlock.text.trim());
         }
       }
     }
   }
 }

 const thoughtSummaryText =
   thoughtSegments.length > 0 ? thoughtSegments.join("\n\n") : null;

 const rawText: string = interaction.output_text || "";
 if (!rawText) {
   throw new Error("Gemini Interactions API returned an empty output_text payload.");
 }

 // Validate against JSON schema using Zod v3.24+ z.fromJSONSchema or direct parse
 const parsedJson = JSON.parse(rawText);
 const dynamicZodValidator =
   typeof (z as any).fromJSONSchema === "function"
     ? (z as any).fromJSONSchema(params.jsonSchema)
     : z.any();

 const validatedData = dynamicZodValidator.parse(parsedJson) as T;

 return {
   parsedOutput: validatedData,
   interactionId: interaction.id,
   thoughtSummaryText,
   totalThoughtTokens:
     typeof interaction.total_thought_tokens === "number"
       ? interaction.total_thought_tokens
       : null,
   latencyMs,
 };
}

function buildTacticalBoardDigest(chess: Chess): string {
 const board = chess.board();
 const tacticalNotes: string[] = [];

 for (const row of board) {
   for (const cell of row) {
     if (!cell) continue;
     const sq = cell.square as Square;
     const whiteAttackers = chess.attackers(sq, "w");
     const blackAttackers = chess.attackers(sq, "b");

     if (cell.color === "w" && blackAttackers.length > 0) {
       tacticalNotes.push(
         `White ${cell.type.toUpperCase()} on ${sq} is attacked by Black from [${blackAttackers.join(", ")}] and defended by White from [${whiteAttackers.join(", ") || "NONE - HANGING PIECE"}].`
       );
     } else if (cell.color === "b" && whiteAttackers.length > 0) {
       tacticalNotes.push(
         `Black ${cell.type.toUpperCase()} on ${sq} is attacked by White from [${whiteAttackers.join(", ")}] and defended by Black from [${blackAttackers.join(", ") || "NONE - HANGING PIECE"}].`
       );
     }
   }
 }

 return tacticalNotes.length > 0
   ? tacticalNotes.join("\n")
   : "No pieces are currently under direct attack.";
}

   for (const cell of row) {
     if (cell) {
       pieces.push({
         id: `${cell.color}-${cell.type}-${cell.square}`,
         type: cell.type,
         color: cell.color,
         square: cell.square as Square,
         captured: false,
       });
     }
   }
 }
 return pieces;
}

export const ProceduralPieceMesh: React.FC<PieceMeshProps> = ({
 type,
 color,
 square,
 isSelected,
 onSelect,
}) => {
 const groupRef = useRef<THREE.Group>(null);
 const geometries = useProceduralChessGeometries();
 const [targetX, , targetZ] = squareToWorldCoords(square);
 const initializedRef = useRef(false);

 useFrame((_, delta) => {
   if (!groupRef.current) return;
   if (!initializedRef.current) {
     groupRef.current.position.set(targetX, 0, targetZ);
     initializedRef.current = true;
     return;
   }

   const pos = groupRef.current.position;
   const dx = targetX - pos.x;
   const dz = targetZ - pos.z;
   const dist = Math.hypot(dx, dz);

   const speed = Math.min(1, delta * 11);
   pos.x = THREE.MathUtils.lerp(pos.x, targetX, speed);
   pos.z = THREE.MathUtils.lerp(pos.z, targetZ, speed);

   // Smooth vertical arc during piece movement or selection hover
   const selectionLift = isSelected ? 0.22 : 0;
   const transitHop = dist > 0.05 ? Math.min(0.55, dist * 0.35) : 0;
   pos.y = THREE.MathUtils.lerp(pos.y, selectionLift + transitHop, speed);
 });

 const materialProps = useMemo(
   () =>
     color === "w"
       ? {
           color: isSelected ? "#60A5FA" : "#F8FAFC",
           roughness: 0.22,
           metalness: 0.08,
           clearcoat: 0.6,
         }
       : {
           color: isSelected ? "#F59E0B" : "#1E293B",
           roughness: 0.28,
           metalness: 0.25,
           clearcoat: 0.7,
         },
   [color, isSelected]
 );

 return (
   <group
     ref={groupRef}
     onClick={(e) => {
       e.stopPropagation();
       onSelect(square);
     }}
   >
     {type === "n" ? (
       <group rotation={[0, color === "w" ? Math.PI / 2 : -Math.PI / 2, 0]}>
         <mesh geometry={geometries.knightBase} castShadow receiveShadow>
           <meshPhysicalMaterial {...materialProps} />
         </mesh>
         <mesh geometry={geometries.knightHead} castShadow receiveShadow>
           <meshPhysicalMaterial {...materialProps} />
         </mesh>
       </group>
     ) : (
       <mesh
         geometry={
           type === "p"
             ? geometries.pawn
             : type === "r"
               ? geometries.rook
               : type === "b"
                 ? geometries.bishop
                 : type === "q"
                   ? geometries.queen
                   : geometries.king
         }
         castShadow
         receiveShadow
       >
         <meshPhysicalMaterial {...materialProps} />
       </mesh>
     )}
   </group>
 );
};

Architectural Conclusions and Production Verification Matrix

This system design resolves the core tension between rich interactive 3D graphics, deterministic board-game rules, and stateful multi-turn LLM execution1. By synthesizing all chess meshes mathematically via THREE.LatheGeometry and THREE.ExtrudeGeometry and tying mesh reconciliation to persistent piece identifiers, the Next.js client avoids external 3D asset bottlenecks while maintaining 60 FPS visual interpolation2. Simultaneously, standardizing all Google AI operations on the Generally Available Interactions API (@google/genai v2.3.0+) with previous_interaction_id state chaining ensures that gemini-4-argon and gemini-3.8-flash retain both their multi-turn conversational context and their encrypted server-side thought signatures without incurring quadratic token overhead1.
